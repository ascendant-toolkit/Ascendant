Development Life Cycle

Coursebook: Chapter 12 · Software development · section 12.1 Program development life cycle

The stages of the program development life cycle, the waterfall and iterative or RAD models, and choosing a model for a scenario, with animations, labs and the real Paper 2 questions from 2021 to 2026.

This page in five sentences

The program development life cycle splits a project into stages: analysis (what is needed), design (how it will work), coding (writing it), testing (does it work) and maintenance (keeping it working). In the waterfall model each stage is finished before the next starts, with the result of one stage passing down to the next and the option of returning to a previous stage. In iterative models, including Rapid Application Development (RAD), working prototypes are built early and improved in cycles with the client involved throughout. Different life cycles exist because projects differ in size, in how clear the requirements are, and in how much the client will be involved. A life cycle makes a project easier to plan, manage and cost because each stage has clear deliverables.

1 · The stages and what happens in each

StageTypical activitiesOutput
AnalysisStudy the current system; interview managers and staff, survey users, observe the system in use; feasibility study; decide the life cycle; write the requirementsProblem definition, requirements specification, documents about the current system (ER or data flow diagrams)
DesignChoose data structures, records and file structures; algorithms, flowcharts and pseudocode; program structure (modules, structure charts, state-transition diagrams); use of library routines; user interface and report layouts; test plan; choice of language and environmentDesign documents and a test plan
CodingWrite the program in a programming language from the design; use an IDE; fix syntax errorsWorking program code
TestingWalkthroughs, dry runs with trace tables, running the program with test data; unit, integration, alpha, beta and acceptance testingTest results; a list of faults
MaintenanceCorrective (fix errors), adaptive (new hardware, rules, requirements) and perfective (improve it)An updated program

Questions give an activity and ask for its stage. Useful anchors: interviewing the client or a feasibility study = analysis; an identifier table, a flowchart, defining records and file structures, choosing a data structure = design; implementing an algorithm or syntax errors occur = coding; a trace table, a walkthrough, test plan results = testing; modifying the program for new hardware = maintenance.

2 · Waterfall

  • The stages run in sequence: analysis, design, coding, testing, maintenance. The result of one stage is the input to the next.
  • Downward arrows: the result of one stage is passed on as the input to the next. Upward arrows: more work is needed at a previous stage to complete the current one (a design fault found in coding).
  • Good: predictable for budget and timeline; all requirements are identified before coding; each stage has clear documents.
  • Poor: no working software until late, so slow to market; late changes to requirements are hard to include; needs high involvement from the client at the start.

3 · Iterative and Rapid Application Development (RAD)

  • Work is divided into small increments or modules; each cycle produces a prototype that the client reviews, then improves.
  • Principles: modules developed in parallel or as prototypes; minimal detailed planning, so requirements can change; flexible; small releases each adding functionality; the client is involved at all stages.
  • Benefits compared with waterfall: quicker development and delivery of usable modules, a prototype at an early stage, easier to change requirements, early review and closer co-operation with the client.
  • Drawbacks: cost and time are difficult to estimate, documentation is often left out, and the client needs to be available (they may keep changing their mind).

4 · Why a life cycle is used

It breaks a large problem into stages that are easier to manage, plan and cost; each stage has clear deliverables; teams can be allocated by stage or module. The choice of life cycle depends on the complexity of the problem, the size and skills of the team, the budget and time available, how fixed the requirements are, and how much the client will be involved.

Common ways to lose marks

  • Putting a design activity (identifier table, choice of data structure) under analysis or coding.
  • Describing a model without a reason: for the scenario, say what it provides (a prototype early, changes easier).
  • Saying "faster" for waterfall or RAD without saying why.
  • Mixing up the arrows: down passes results on; up means returning to an earlier stage.

Examples are explained in general terms. Check current details before quoting them in an exam answer.

A large bank system

Requirements are fixed by law, cost has to be predictable, and each stage is signed off before the next: waterfall.

Exam use: waterfall.

A start-up's new app

It releases a basic version quickly, listens to users and adds features every few weeks.

Exam use: iterative / RAD.

A school website

The principal has ideas but not the details, so a first version is built and changed after review.

Exam use: prototype and iteration.

A game after release

Bugs are fixed with updates (corrective), and support for a new console is added later (adaptive).

Exam use: maintenance.

Top tips

  • Anchor each stage. Interview: analysis. Flowchart: design. Code: coding. Trace table: testing. New hardware: maintenance.
  • Prototype early. That is the reason for RAD in a scenario question.
  • Mention the scenario. Use the facts given: requirements change, client unclear.
  • Two arrow directions. Down passes on; up returns.
  • RAD drawbacks. Cost and time are hard to estimate; documentation is often missing.
  • Design is wider than you think. Data structures, algorithms, modules, interface, test plan.
