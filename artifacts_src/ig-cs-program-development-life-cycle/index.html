Program Development Life Cycle

Analysis, design, coding and testing, with abstraction, decomposition and iterative testing.

The big idea

A program is built in four stages: analysis, design, coding and testing. Abstraction and decomposition make a big problem manageable, and testing can send you back to fix errors.

7.1 The program development life cycle

Writing a program is not just typing code. The program development life cycle breaks the job into four stages: analysis, design, coding and testing. Problems found in a later stage often send you back to an earlier one, so it is a cycle.

StageWhat happens
AnalysisWork out what the problem is and what the program must do. Use abstraction and decomposition, and identify the requirements.
DesignPlan the solution before writing code. Use decomposition, structure diagrams, flowcharts and pseudocode.
CodingWrite the program code in a programming language. Test each part as it is written (iterative testing).
TestingRun the whole program with test data and compare the results with what was expected. Fix any errors.

Analysis

Abstraction

Abstraction means keeping the details that matter and hiding or removing the ones that do not. A map of the London Underground ignores real distances and street layouts and keeps only stations and connections.

Decomposition

Decomposition means breaking a big problem into smaller parts that are easier to understand, solve and test separately. Each part can then be broken down again.

Analysis also means identifying the problem and its requirements: what the inputs are, what processing must happen, what outputs are needed, what data must be stored, and any limits (such as who will use it).

Design

Design turns the analysis into a plan. The problem is decomposed into parts, and each part is described with one or more of these:

  • Structure diagram: boxes showing the parts of the system, from the whole problem at the top down to the smallest tasks.
  • Flowchart: shapes and arrows showing the steps and decisions of an algorithm.
  • Pseudocode: the algorithm written in structured English that looks like code but is not tied to a language.

Each of these has its own page: 7.2 covers design methods.

Coding and iterative testing

In the coding stage the design is written as program code. Good programmers do not wait until the end: they test each small part as they write it, fix the errors, then move on. This repeated cycle of writing and testing is iterative testing.

Testing

Testing checks that the finished program works. The program is run with test data (chosen values, with the results worked out in advance). The actual results are compared with the expected results. Where they differ, there is an error to find and fix, which may mean going back to coding or even design.

Worked example: a school canteen pre-order app

StageExample tasks
AnalysisStudents must choose items before school. Inputs: name, items. Output: an order list for the kitchen. Ignore irrelevant detail (abstraction). Split into ordering, paying and kitchen display (decomposition).
DesignStructure diagram with the three parts. Flowchart for the payment check. Pseudocode for the total price.
CodingWrite the ordering part and test it. Then the payment part and test it. Then join them.
TestingRun the full app with normal, extreme and abnormal orders. Compare with expected results. Fix bugs.
Do not confuseDecomposition appears in both analysis and design. Abstraction is part of analysis. Flowcharts and pseudocode belong to design, not coding.

App updates

Exam-style questions

Open each question for reminders, a model answer and common mistakes. Each underlined phrase earns one mark; the number shows which mark point it is.

Q1 State 4 marks State the four stages of the program development life cycle, in order.
ReminderOne word each.
Analysis Design Coding Testing
Common mistakeWriting "planning" or "implementation". Use the exact stage names.
Q2 Describe 3 marks Describe what happens in the analysis stage.
ReminderProblem, requirements, and the two techniques.
The problem is identified and the requirements of the program are worked out (inputs, processing, outputs, storage). Abstraction is used to remove unnecessary detail and keep what matters. The problem is decomposed (broken down) into smaller parts.
Common mistakeDescribing designing or writing code. Analysis is about understanding the problem.
Q3 Explain 3 marks Explain what is meant by abstraction and give an example.
ReminderSay what is kept and what is hidden, then an example.
Abstraction means removing or hiding unnecessary details. Only the details needed to solve the problem are kept (focusing on what matters). Example: a map of the underground shows stations and lines but not the streets above (or any suitable example).
Common mistakeConfusing it with decomposition. Abstraction removes detail; decomposition splits into parts.
Q4 Explain 3 marks Explain why a large problem is decomposed into smaller parts.
ReminderEasier, separate, parallel.
Each smaller part is easier to understand and solve than the whole problem. Each part can be tested separately (so errors are easier to find). Different programmers can work on different parts at the same time.
Common mistakeWriting only "it is easier". Say why: smaller, testable, shareable parts.
Q5 State 3 marks State three methods that can be used to design a solution to a problem.
ReminderThree named tools.
Structure diagram Flowchart Pseudocode
Common mistakeNaming a programming language. Design methods are tools used before coding.
Q6 Describe 3 marks Describe what is meant by iterative testing in the coding stage.
ReminderTested while writing, repeatedly.
Parts of the program are tested as they are written (not only at the end). Any errors found are fixed. The cycle of writing, testing and fixing is repeated for each part.
Common mistakeDescribing the final testing stage. Iterative testing happens during coding.
Q7 Explain 3 marks During testing, the program gives different results from those expected. Explain what the programmer should do next.
ReminderFind the cause, go back, retest.
Find the cause of the error by checking the code and the test data. Return to the coding stage (or design if the plan was wrong) and correct it. Test again with the same test data to check the error is fixed.
Common mistakeSaying "finish the program" or "ignore it". Errors send you back to an earlier stage.

Top tips

  • Four stages, in order: analysis, design, coding, testing.
  • Abstraction = remove detail. Decomposition = break into parts. Never swap them.
  • Flowcharts, structure diagrams and pseudocode are design methods.
  • Iterative testing happens during coding; test data is used in the testing stage.
  • It is a cycle: errors found in testing send you back to coding or design.
