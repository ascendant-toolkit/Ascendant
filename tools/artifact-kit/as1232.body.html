Program Maintenance

Coursebook: Chapter 12 · Software development · section 12.3 Program testing and maintenance

Corrective, adaptive and perfective maintenance, reasons for each and documentation that helps maintenance, with animations, labs and the real Paper 2 questions from 2021 to 2026.

This page in five sentences

Maintenance is the last stage of the program development life cycle: changing a program after it has been released. Corrective maintenance fixes errors (bugs) found while the program is in use. Adaptive maintenance changes the program to cope with a change in its environment or requirements, such as new hardware, new technology, a changed library module or a change in the law. Perfective maintenance improves the program without changing what it does, for example to make it faster or easier to use. Good documentation (an identifier table, design documents and comments) made during design and coding makes all three types easier.

1 · The three types

TypePurposeTypical reasons
CorrectiveFix faultsThe program does not operate as expected, contains a bug, or unexpected bugs are reported after it is installed (passwords are not hidden)
AdaptiveChange the program to fit a change outside itA change in the user requirements; new technology or new hardware; changes made to library modules used; a change in the law (legislation); a new version of a standard such as HTML
PerfectiveMake the program better without changing what it doesImprove the speed of response; make the program more efficient or easier to use; improve the user interface

Use the question to decide: a fault reported by users is corrective; a new requirement, new hardware or a change in the law is adaptive; a change that improves speed or efficiency is perfective.

2 · Why documentation matters

  • A maintenance programmer may not be the person who wrote the program. They need to find what each part does.
  • An identifier table records each variable with its name, data type, purpose and an example value or initial value.
  • Design documents (structure charts, flowcharts, state-transition diagrams, pseudocode) and comments in the code show how the program works, so a change can be made without introducing new faults.
  • Meaningful identifier names, indentation, white space and comments make the code easier to understand and to change.

3 · Where maintenance fits

After testing and release, maintenance can go on for many years. A change may mean going back through analysis, design, coding and testing: even a small change has to be tested again so that it has not caused a new fault elsewhere.

Common ways to lose marks

  • Calling a bug fix adaptive: fixing faults is corrective.
  • Describing perfective maintenance as adding a new feature required by a change in the requirement (that is adaptive).
  • Giving a reason without naming the type, or a type without a matching reason: the marks are dependent.
  • Writing "easier to read" for documentation: say what is recorded (purpose of each variable) and who uses it (the maintenance programmer).

Phone app updates

Some updates fix bugs (corrective), some support a new phone or operating system (adaptive) and some make the app faster (perfective).

Exam use: all three types.

Tax software every year

When the tax rules change, the program has to be changed: adaptive maintenance in response to legislation.

Exam use: adaptive.

A game patch after launch

Players report that the score is wrong, and the developer fixes it, retests and releases a patch.

Exam use: corrective.

A website redesign for speed

The pages are rewritten so they load faster without changing what they do.

Exam use: perfective.

Top tips

  • Three types. Corrective fixes, adaptive adapts, perfective improves.
  • A reason for each. Marks depend on the type and the matching reason.
  • Adaptive reasons. Requirements, technology or hardware, library modules, law.
  • Perfective is not new. Same function, better speed or use.
  • Documentation. An identifier table with purpose, type, example.
  • Retest. Every change needs testing.
